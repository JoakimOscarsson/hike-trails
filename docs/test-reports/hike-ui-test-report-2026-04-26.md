## Executive Summary

The app is broadly functional: it loads, displays both trail systems, route selection works, favorites persist, route builder/detail navigation works, normal route data currently serves with 2xx responses, and the tested Sörmlandsleden UI content matched the underlying data.

The most important issues are:

1. Leaflet can throw an uncaught runtime exception during map remount/transition flows.
2. Trail-system maps fetch and draw every section route on each selected-range render, which creates large performance cost and makes unrelated route failures able to break selected maps.
3. Narrow desktop widths from about 901px to 1024px overflow horizontally.
4. A no-results filter state leaves the previous route detail visible, creating a mismatch between list and content.
5. Several interactive/toggled states need better accessibility semantics.

## Findings

### P1: Leaflet Runtime Exception During Normal Interaction

Severity: High

Reproduction:
1. Open the app.
2. Switch between Roslagsleden and Sörmlandsleden.
3. Change distance filters and move between route builder/detail views while the map is present.

Expected:
The map should update without uncaught exceptions.

Actual:
Agents A and C captured an uncaught Leaflet exception:

```text
TypeError: Cannot read properties of undefined (reading '_leaflet_pos')
```

The stack included Leaflet transition methods such as `_getMapPanePos`, `_getNewPixelOrigin`, `_move`, and `_onZoomTransitionEnd`.

Likely cause:
`TrailSystemMap` and `RouteMap` remove and recreate Leaflet maps during React effect cleanup. A pending Leaflet zoom/move transition can finish after `map.remove()`.

Likely source areas:
- /Users/joakim/Documents/New project/src/main.tsx:483
- /Users/joakim/Documents/New project/src/main.tsx:587
- /Users/joakim/Documents/New project/src/main.tsx:740

Suggested fix:
Avoid full map remounts for marker/filter updates where possible. When removing a map, stop transitions/listeners before removal, and guard async route drawing so it cannot update a removed map.

### P1: Trail-System Maps Fetch/Draw Every Section Route

Severity: High for performance and resilience

Reproduction:
1. Open the app.
2. Select Sörmlandsleden.
3. Choose a short selected route such as the `0-5 km` distance filter.
4. Inspect route network requests or map SVG path count.

Expected:
The map should prioritize selected route sections and only draw unrelated overview routes intentionally and safely.

Actual:
For Sörmlandsleden, even a one-stage selected route produced around 100 SVG paths. The map fetches route files for all trail-system sections during each selected-range render.

Impact:
- Large network/render cost for small route plans.
- Any unrelated missing/malformed route file can break the selected map.
- Interacts with the Leaflet remount issue above.

Likely source area:
- /Users/joakim/Documents/New project/src/main.tsx:621

Suggested fix:
Fetch/draw selected sections first, tolerate each section failure independently, and lazy-load or separately guard overview/unselected sections.

### P1/P2: Missing Trail-System Route Can Blank Selected Map Overlays

Severity: High for resilience, currently latent because all tested resources exist

Reproduction used by Agent C:
1. Intercept `/routes/sormlandsleden-stage-40.geojson` and return 404.
2. Select Sörmlandsleden.
3. Set Distance to `0-5 km`, selecting `Stage 40: Dragsviken to Mellsjön`.

Expected:
The app should show a route-load warning while still rendering available facilities, access points, and commute markers where possible.

Actual:
The UI still says `Route + facilities` and `1 main · 4 km`, but the map falls back to a generic marker. It loses the route path, start/end markers, `Mellsjön shelter`, `Mellsjön toilet`, and commute markers.

Likely cause:
`Promise.all` over all trail-system sections throws the whole draw operation if any route fetch fails.

Suggested fix:
Use per-section error handling and render partial results. Update map status when the selected route geometry fails.

### P2: Active Filters Can Contradict Selected Route Summary

Severity: Medium

Reproduction:
1. Load the app.
2. Set Distance to `20+ km`.
3. Set Time to `6+ days`.

Expected:
The selected route summary should align with active filters, or the app should clearly communicate that filters only affect the route list.

Actual:
The filter controls show `20+ km` / `6+ days`, while the selected route can remain a day-hike-length route such as `10.5 km` and `Day hike`.

Suggested fix:
Either update selected route state to match active filters consistently, or visually separate list filters from route-builder state.

### P2: Narrow Desktop Horizontal Overflow

Severity: High visual/layout bug

Reproduction:
1. Open the default route-builder view.
2. Use viewport widths around 901px, 960px, or 1024px.

Expected:
The page should fit within the viewport.

Actual:
The document width expands to about 1100px. `.builder-workspace` and `.builder-toolbar` extend offscreen. Agent B confirmed this at 901px, 960px, and 1024px. The layout was clean again at 900px and 1100px.

Likely cause:
The tablet media query ends at 900px, but the desktop shell has a 280px sidebar plus builder grid tracks with minimums around 360px and 430px, plus gaps and padding.

Likely source areas:
- /Users/joakim/Documents/New project/src/styles.css:29
- /Users/joakim/Documents/New project/src/styles.css:703
- /Users/joakim/Documents/New project/src/styles.css:1254

Suggested fix:
Extend the tablet/stacked breakpoint to the actual minimum width required by the desktop builder, or add a targeted 901px-1099px rule that stacks/relaxes the builder grid.
